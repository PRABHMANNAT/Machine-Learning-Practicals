# Flask Handbook Bridge — From Python Functions to Web Apps

This guide turns the `flask/` folder into a beginner course. It keeps the original tiny apps, then grows toward forms, APIs, sessions, blueprints, SQLite, authentication, and deployment.

## 1. Flask explained like you are 5

Imagine a restaurant:

- The **browser** is a customer.
- An **HTTP request** is the customer's order.
- Flask is the **receptionist** who reads the requested URL.
- A **route** is a rule saying which cook (Python function) handles that order.
- An **HTTP response** is the finished plate returned to the customer.

Flask is a Python web **framework**. It provides the request/response machinery while letting you choose your database, project structure, and extra tools.

## 2. Install and run safely

Create and activate a virtual environment, then install Flask:

```text
python -m venv .venv
# Windows PowerShell
.venv\Scripts\Activate.ps1
python -m pip install Flask
```

From the `flask/` directory:

```text
python app.py
```

Visit the local URL printed in the terminal. Stop with `Ctrl+C`.

You can also use Flask's CLI:

```text
flask --app app run --debug
```

`--debug` reloads changed code and shows detailed errors. **Never expose the interactive debugger publicly.**

## 3. Smallest useful app

```python
from flask import Flask

app = Flask(__name__)

@app.get("/")
def home():
    return "Hello from Python!"

if __name__ == "__main__":
    app.run(debug=True)
```

Step by step:

1. `Flask(__name__)` creates the application and helps Flask find resources.
2. `@app.get("/")` connects the home URL to the function below it.
3. `home()` returns a response body.
4. The main guard starts the development server only when this file is run directly.

## 4. Requests, responses, and HTTP

An HTTP request contains a method, path, headers, optional query string, cookies, and sometimes a body. A response contains a status code, headers, and body.

| Method | Typical meaning | Safe/idempotent idea |
|---|---|---|
| `GET` | read/show something | should not change server state |
| `POST` | create/submit an action | can create a new result each time |
| `PUT` | replace/update a resource | repeated same request should settle to same state |
| `PATCH` | partially update | update selected fields |
| `DELETE` | remove | repeated deletion ends in resource absent |

Common status codes:

| Code | Meaning |
|---:|---|
| 200 | OK |
| 201 | Created |
| 204 | Success with no body |
| 302 | Temporary redirect |
| 400 | Invalid client input |
| 401 | Not authenticated |
| 403 | Authenticated but forbidden |
| 404 | Not found |
| 409 | Conflict |
| 415 | Unsupported media type |
| 500 | Unexpected server error |

Flask converts several Python return styles into responses:

```python
return "Hello"                         # text/html, status 200
return {"status": "ok"}               # JSON response
return render_template("home.html")    # rendered HTML
return "Missing", 404                  # body + status
return response_object                  # full control
```

## 5. Routes and dynamic routes

```python
@app.get("/hello/<name>")
def hello(name):
    return f"Hello {name}"

@app.get("/orders/<int:order_id>")
def order(order_id):
    return {"order_id": order_id}
```

Useful converters include `string` (default), `int`, `float`, `path`, and `uuid`. A route that expects an integer will not match letters.

Query strings live after `?` and do not decide route matching:

```python
from flask import request
language = request.args.get("language", "English")
```

Prefer `url_for("endpoint", value=...)` over hand-written URLs. It understands routes, converters, script prefixes, and endpoint names.

## 6. Templates and Jinja2

Templates keep HTML separate from Python.

```python
return render_template("greeting.html", name="Asha", scores=[80, 90])
```

```jinja2
<h1>Hello {{ name }}</h1>
{% for score in scores %}
  <p>{{ score }}</p>
{% endfor %}
```

| Syntax | Job |
|---|---|
| `{{ value }}` | print an expression |
| `{% if ... %}` | control flow |
| `{% for ... %}` | loop |
| `{# ... #}` | template comment |
| `{{ value|title }}` | apply a filter |

Jinja auto-escapes normal HTML template values. Do not add `|safe` to untrusted text. Template inheritance removes repeated page shells:

```jinja2
{% extends "base.html" %}
{% block content %}<h1>Page</h1>{% endblock %}
```

## 7. Static files

CSS, JavaScript, fonts, and local images belong under `static/`:

```jinja2
<link rel="stylesheet" href="{{ url_for('static', filename='css/style.css') }}">
<script src="{{ url_for('static', filename='js/app.js') }}" defer></script>
```

In large production deployments, a CDN or reverse proxy often serves static assets.

## 8. GET, POST, and forms

```python
@app.route("/form", methods=["GET", "POST"])
def form():
    if request.method == "POST":
        name = request.form.get("name", "").strip()
        if not name:
            return "Name required", 400
        return redirect(url_for("success", name=name))
    return render_template("form.html")
```

- `request.form` reads form-encoded values.
- `request.files` reads uploads.
- `request.get_json()` reads JSON bodies.
- Browser attributes such as `required` improve experience, but attackers can bypass them. **Validate again on the server.**
- Use Post/Redirect/Get after successful forms so refresh does not resubmit.
- State-changing forms need CSRF protection in real apps (for example, Flask-WTF or another carefully implemented strategy).

## 9. JSON and REST APIs

A resource-oriented API uses nouns in URLs and methods for actions:

```text
GET    /items        list
GET    /items/7      retrieve
POST   /items        create
PUT    /items/7      replace/update
DELETE /items/7      delete
```

Validate the JSON type and required fields, return useful status codes, and keep error shapes consistent. Never trust IDs or ownership claims supplied by clients. Authentication says **who** the caller is; authorization decides **what** they may do.

The improved `flask/api.py` is an in-memory CRUD API. Its list resets at restart; persistent data belongs in a database.

## 10. Redirects and flash messages

```python
from flask import flash, redirect, url_for

flash("Saved!", "success")
return redirect(url_for("index"))
```

Flash messages are stored temporarily in the session and displayed on the next request. Avoid open redirects: never redirect blindly to a user-provided external URL.

## 11. Cookies and sessions

A cookie is a small browser value sent with matching requests. A Flask session normally stores signed data in a cookie: users can read it, but cannot modify it without invalidating the signature. Therefore, do not store secrets or large values in it.

```python
app.config["SECRET_KEY"] = os.environ["FLASK_SECRET_KEY"]
session["user_id"] = user.id
```

Security settings commonly include `SESSION_COOKIE_HTTPONLY`, `SESSION_COOKIE_SECURE` under HTTPS, and `SESSION_COOKIE_SAMESITE`. Rotate/manage secrets deliberately; changing the secret invalidates existing sessions.

## 12. Error handling

```python
from flask import abort

@app.get("/items/<int:item_id>")
def item(item_id):
    item = find_item(item_id)
    if item is None:
        abort(404)
    return item

@app.errorhandler(404)
def not_found(error):
    return render_template("404.html"), 404
```

Catch expected input/domain failures near their boundary. Let unexpected bugs reach a central handler/log. Do not return stack traces, database details, or secrets to users.

## 13. SQLite/database basics

Open one connection for the request, store it on Flask's `g`, and close it in `teardown_appcontext`. Always parameterize values:

```python
db.execute("SELECT * FROM tasks WHERE id = ?", (task_id,))
```

Never use an f-string for untrusted SQL values. Commit intentional writes, rollback failed transactions, use constraints, add migrations as the schema evolves, and move beyond SQLite when write concurrency/operations require it.

`demos/database_crud.py` is a complete tiny persistent CRUD project.

## 14. Authentication basics

Passwords must be salted and hashed with a password-hashing function; never stored as plaintext.

```python
from werkzeug.security import generate_password_hash, check_password_hash

stored = generate_password_hash(password)
valid = check_password_hash(stored, submitted_password)
```

Authentication is a system, not one login route. Real systems need rate limiting, secure recovery, verified identities where appropriate, session expiry/revocation, CSRF defense, authorization checks, audit trails, and HTTPS. Consider a mature library or external identity provider.

## 15. Blueprints and application factories

A Blueprint is a labeled box of routes. It helps split a large application by feature. An application factory creates configured app instances for development, testing, and production.

```python
def create_app(test_config=None):
    app = Flask(__name__)
    app.register_blueprint(pages)
    return app
```

The `demos/blueprint_app/` package shows page/API blueprints and `demos/run_blueprints.py` starts it.

## 16. Recommended project structure

```text
project/
├── app_package/
│   ├── __init__.py       # create_app
│   ├── auth.py           # auth Blueprint
│   ├── items.py          # feature Blueprint
│   ├── templates/
│   └── static/
├── tests/
├── instance/             # local runtime data; normally ignored
├── wsgi.py               # server entry point
├── requirements.txt
└── .env.example          # names only, never real secrets
```

Keep route functions small: validate the request, call ordinary service/data functions, then build a response.

## 17. Deployment

Flask's development server is not the production server. A deployment usually needs:

1. a production WSGI server such as Waitress (portable) or Gunicorn (commonly Unix);
2. environment variables for secrets/configuration;
3. HTTPS, often at a reverse proxy/platform;
4. logging, monitoring, health checks, and backups;
5. dependency pinning and a repeatable build;
6. correct proxy settings and trusted host/security headers;
7. multiple workers only after understanding state and database limits.

Example:

```text
python -m pip install waitress
waitress-serve --call wsgi:create_app
```

Do not keep important mutable state in global Python lists: different workers do not share it, and restarts erase it. Use a database/cache/service designed for shared state.

## 18. Common mistakes

| Mistake | Better habit |
|---|---|
| public `debug=True` | production WSGI server, debug off |
| trusting browser validation | validate on server too |
| string-building SQL | parameterized queries |
| plaintext passwords | proven password hashing |
| hard-coded secret keys | environment/secret manager |
| giant route functions | service/data helper layers |
| global list as production DB | persistent datastore |
| returning 200 for every error | meaningful status codes |
| unbounded upload/body | configure limits and validate type |
| `|safe` on user content | rely on escaping/sanitize intentionally |
| no CSRF defense | protect state-changing browser requests |
| blind `next` redirect | allow only safe local targets |

## 20. Key takeaways

- A route maps a method + URL to a Python view function.
- Requests are untrusted input; responses should communicate honest status/content.
- Templates render HTML; Jinja escaping is a safety feature.
- Use `url_for`, server validation, Post/Redirect/Get, and CSRF protection.
- Keep shared data in a database, not a global list.
- Sessions need a strong secret; passwords need proven hashing.
- Blueprints and factories organize growing applications.
- Test with Flask's test client and deploy behind a production WSGI server.
